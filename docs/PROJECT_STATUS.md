# 项目状态与恢复开发路线

更新日期：2026-09-26。

用途：帮助单人开发者在间隔一段时间后快速恢复开发。依据现有代码目录、依赖声明、v1.0.0 基线文档及本次环境检查整理，未进行完整业务验收。

状态口径：下文“已完成”指已有代码实现或文档明确列为交付，不代表所有场景已测试通过；“未完成 / 待验证”区分代码明确未实现、历史文档待办和本次尚未验证的事项。

### 开发环境与版本管理

- 最初启动失败的直接原因：脚本回退到全局 Python 3.14，导入 `django` 失败；当时该环境缺少后端 requirements 中的依赖。
- 最新检查已发现 `adminAPI/.venv/`，其 `pyvenv.cfg` 记录 Python 3.12.0，基础路径为 `D:\jdk\python312`。不要继续把“项目没有虚拟环境”当作当前事实；该环境依赖是否完整、四服务是否成功启动仍待验证。
- 当前根目录没有 `.git`，没有可读取的本地提交历史或项目远程配置。
- 根目录 `.gitignore` 目前尚未创建；此前只提供了建议内容，没有实际执行 Git 初始化。
- 已发现实际环境配置含非空敏感字段。首次提交前需忽略 `.env`、部署实际配置、数据库、上传文件、虚拟环境和发布包，并检查示例配置是否脱敏。

## 四、下一步路线

按“先恢复运行，再建立可追溯基线，最后推进业务”的顺序处理，避免同时扩大改动范围。

### 第一步：恢复本地开发

- [ ] 使用现有 `adminAPI/.venv` 检查并补齐 `adminAPI/requirements.txt` 依赖。
- [ ] 在根目录执行 `cmd /c start-dev.bat --check`；通过后双击启动脚本。
- [ ] 确认四个窗口均正常运行，三端页面和 API 可访问，停止脚本能停止对应服务。
- [ ] 核对数据库迁移状态；执行迁移前备份现有 SQLite 数据库，不盲目重建或重复导入演示数据。
- [ ] 在本文记录实际启动结果和解决的问题，不把静态检查通过当作完整运行成功。

### 第二步：首次接入 Git

- [ ] 保存根目录 `.gitignore`，审查 `.env.example` 等模板中的敏感内容。
- [ ] 单独备份本地数据库和上传文件，确认它们不进入 Git。
- [ ] 初始化根目录仓库，检查暂存清单和差异，创建当前项目基线提交。
- [ ] 如需远程备份，连接私有空仓库后推送。
- [ ] 不直接为当前代码打历史 `v1.0.0` 标签，除非已核实与该基线一致。

### 第三步：验证现有核心流程

- [ ] 运行现有后端测试、商城单测及 E2E；记录环境条件和失败项。
- [ ] 手动验证：三端登录 → 商品浏览 → 购物车 → 下单 / 模拟支付 → 商家发货 → 收货 / 售后。
- [ ] 验证角色权限、商家数据隔离、WebSocket 聊天、通知和红点。
- [ ] 将发现的问题整理成具体待办，优先修复阻塞主流程的问题。

### 第四步：按实际需要补齐能力

- [ ] 核实库存、促销通知的剩余工作，更新过时文档。
- [ ] 如计划真实交易，再明确支付、退款、对账和物流联调范围。
- [ ] 按需求评估历史基线中的限流、权限细化等待办，不为恢复开发引入额外架构。
- [ ] 每完成一个可验证改动就提交 Git；阶段性更新本文和变更记录。
